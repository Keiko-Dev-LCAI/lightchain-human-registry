# ZKPassport — research from official sources

- **Date:** 2026-11-17
- **Method:** read-only web reading of ZKPassport's own website, GitHub org and docs source. Nothing was cloned, downloaded, installed or signed up for. No blockchain calls were made for this step.
- **Owner:** KeikoDev.
- **Marking:** anything not confirmed in an official source is marked **UNCONFIRMED**.

---

## Plain-language summary

1. **Will it fit on Lightchain?** Very likely yes.
   - ZKPassport's verifier already runs live on Ethereum mainnet and Base.
   - It uses only the math Lightchain already passed on 2026-11-17 (BN254 pairing plus modexp).
   - ZKPassport does not publish an exact gas number, so the figure itself is UNCONFIRMED. A typical verification should still be a small fraction of Lightchain's 60,000,000 block gas limit.
2. **Can we deploy it ourselves?** Yes, the license allows it.
   - Everything is Apache-2.0, which allows copying and redeploying. Keep their license notices.
   - Their own README says the Solidity project is meant to deploy "on any EVM chain".
   - No chain ID is hard-coded in the verifier contracts we read.
3. **The real catch: someone has to keep the passport "trust list" current on Lightchain.**
   - Every proof points to a certificate list (the "certificate registry root") and a circuit list (the "circuit registry root").
   - On Ethereum and Base, ZKPassport's own "oracle" wallet posts new roots.
   - On Lightchain, someone would need to copy ("mirror") those roots over regularly, using a wallet given the oracle role. If the copy falls behind, new proofs fail.
   - This is the job that would ideally move to the Lightchain team or the DAO.
4. **One code per document, per app.**
   - The code (the "unique identifier", also called the nullifier) comes from the passport data plus the website **domain** plus a **scope** name.
   - The same passport always gives the same code for the same domain and scope. That is what lets us block a second wallet and move a badge to a new wallet.
   - The domain is part of the code. If the registry's website domain changes later, everyone gets new codes. Pick the domain once and keep it forever (a DAO-held domain is ideal).
5. **Test mode exists.**
   - The ZKPassport app has a hidden Developer Mode with fake passports from the made-up "Zero Knowledge Republic".
   - Fake proofs always have the code `1`, and the contracts refuse them unless dev mode is on.
   - This is a good reference for our browser-only demo.
6. **One SDK gap.** The SDK's "bind to chain" option only lists certain chains (Ethereum, Base, Arbitrum and others), not Lightchain. Workaround: bind the wallet address and put "lightchain:9200" in the custom-data field. Whether the button accepts chain ID 9200 directly is UNCONFIRMED.

## 1. Verifier contracts

**Where they are**
- **Proof verifiers (UltraHonk):** `zkpassport/circuits` → `src/solidity/src/ultra-honk-verifiers/`
  - Files: `OuterCount4.sol` … `OuterCount13.sol`, `OuterAttestedIdCount2–11.sol`, `OuterAadhaarCount2–11.sol`. Each source file is about 311–327 KB.
  - https://github.com/zkpassport/circuits/tree/main/src/solidity/src/ultra-honk-verifiers
- **Wrapper contracts:** `zkpassport/zkpassport-packages` → `packages/registry-contracts/src/`
  - Files: `RootVerifier.sol`, `SubVerifier.sol`, `VerifierHelper.sol`, `RootRegistry.sol`, `RegistryInstance.sol`, `ProtocolController.sol`, `lib/*`.
  - These are pulled into the circuits repo as a git submodule.
  - https://github.com/zkpassport/zkpassport-packages/tree/main/packages/registry-contracts/src

**Solidity version**
- The project pins `solc = "0.8.30"`, optimizer on, 200 runs, `bytecode_hash = "none"`. Source: https://raw.githubusercontent.com/zkpassport/circuits/main/src/solidity/foundry.toml
- The proof verifiers declare `pragma solidity ^0.8.27`. The registry contracts declare `^0.8.30`.

**License**
- The proof verifiers are `SPDX-License-Identifier: Apache-2.0`, "Copyright 2022 Aztec". They are generated by Aztec's Barretenberg.
- The registry contracts are Apache-2.0, "Copyright © 2026 ZKPassport".
- Both repos are listed as Apache-2.0 on GitHub.
- Sources:
  - https://raw.githubusercontent.com/zkpassport/circuits/main/src/solidity/src/ultra-honk-verifiers/OuterCount4.sol
  - https://raw.githubusercontent.com/zkpassport/zkpassport-packages/main/packages/registry-contracts/src/SubVerifier.sol

**Proving system**
- UltraHonk proofs from Aztec's Barretenberg backend; circuits are written in Noir. Source: docs FAQ, https://raw.githubusercontent.com/zkpassport/zkpassport-docs/main/docs/faq.md
- The verifier contract is named `HonkVerifier`.
  - `OuterCount4` constants: `LOG_N = 22`, `CIRCUIT_SIZE = 4194304`, `NUMBER_PUBLIC_INPUTS = 18`.
  - It verifies on BN254 using ecAdd, ecMul and ecPairing, plus modexp for field inverses. Lightchain passed all four on 2026-11-17.

**What a verify call takes**
- **Low-level proof verifier:** `verify(bytes proof, bytes32[] publicInputs) → bool`. Source: `OuterCount4.sol`, `IProofVerifier.sol`.
- **App-facing entry point:** `RootVerifier.verify(ProofVerificationParams) → (bool verified, bytes32 uniqueIdentifier, IZKPassportHelper helper)`.
  - `version` (bytes32) selects the sub-verifier.
  - `proofVerificationData`:
    - `vkeyHash` picks which `OuterCountN` verifier to use.
    - `proof` is the bytes.
    - `publicInputs` is a `bytes32[]`, laid out as: `[0]` certificate registry root, `[1]` circuit registry root, `[2]` current date, `[3]` scope (from domain), `[4]` subscope (service scope), `[5..]` param commitments, then the last four are nullifier_type, scoped_nullifier, oprf_pk_hash and verification_method.
  - `committedInputs` (bytes) holds the preimages of the commitments: disclosed data, bound wallet and chain, age checks and so on.
  - `serviceConfig` holds `validityPeriodInSeconds`, `domain`, `scope` and `devMode`.
  - Sources:
    - Docs: https://raw.githubusercontent.com/zkpassport/zkpassport-docs/main/docs/getting-started/onchain.md
    - Index constants: https://raw.githubusercontent.com/zkpassport/zkpassport-packages/main/packages/registry-contracts/src/lib/Constants.sol
- **Proof size:** fixture `valid_proof.hex` is 19,776 hex characters, about 9.9 KB of bytes. Source: https://github.com/zkpassport/circuits/tree/main/src/solidity/test/fixtures

**Gas**
- **No published gas figure was found.** UNCONFIRMED.
  - Their test `test/ZKPassportRootVerifier.t.sol` measures `RootVerifier.verify` with `vm.startSnapshotGas`/`logGas`, but no gas snapshot file is committed.
  - Source: https://raw.githubusercontent.com/zkpassport/circuits/main/src/solidity/test/ZKPassportRootVerifier.t.sol
- **Estimate** (not from ZKPassport): an UltraHonk verification of this size is commonly a few million gas. Calldata for a ~10 KB proof is roughly 100–200k gas.
- **Evidence that it fits:** the same verifiers are deployed and used on Ethereum mainnet. Contract addresses are in `deployments/addresses-1.json` and `deployment-1.json`. Ethereum has a smaller per-transaction cap than Lightchain's 60M block, and Ethereum's 24 KB contract-size limit also applies there, so the bytecode fits that limit too.
- **Fits under Lightchain's 60M block gas limit:** **yes, with high confidence** (inferred). The exact number is UNCONFIRMED until measured.

**Deployed addresses (Ethereum / Base, for reference only; we would deploy our own)**

## 2. Certificate registry

**How roots are stored**
- `RootRegistry.sol` maps a `registryId` to a `RegistryInstance`. IDs: `1` certificate, `2` circuit, `3` sanctions, `4` attestation revocation (from `Constants.sol`).
- Each `RegistryInstance` stores:
  - `latestRoot`
  - `historicalRoots[root]` = validFrom, validTo, revoked, leaves, IPFS `cid`, three metadata slots
  - `rootByIndex`, `indexByRoot`
- Sources:
  - https://raw.githubusercontent.com/zkpassport/zkpassport-packages/main/packages/registry-contracts/src/RootRegistry.sol
  - https://raw.githubusercontent.com/zkpassport/zkpassport-packages/main/packages/registry-contracts/src/RegistryInstance.sol

**How roots are updated**
- Only the `oracle` address can call `updateRoot(newRoot, currentRoot, timestamp, leaves, cid)`, `updateRootWithMetadata(...)` or `batchUpdateRoots(...)`.
- `admin` can change the oracle, guardian and admin. `admin` or `oracle` can revoke a root or change the validation mode. `admin` or `guardian` can pause; only `admin` can unpause.
- Root validation modes:
  - `LATEST_ONLY`
  - `LATEST_AND_PREVIOUS`
  - `VALID_AT_TIMESTAMP` (checked against the proof's own date)
  - `VALID_WITHIN_WINDOW`
- Each proof is checked against **both** the certificate root and the circuit root (`SubVerifier._validateCertificateRoot`, `_validateCircuitRoot`).
- Android device-attested proofs (FaceMatch, "tier 2") also check an attestation-revocation root (`_verifyAttestationRevocation`).

**Who controls it on Ethereum and Base**
- The root registry is at `0x1D0000020038d6E40E1d98e09fA1bb3A7DAA8B70` on both.
- The **current admin, oracle and guardian addresses of that registry are UNCONFIRMED.** They are not listed in the repo files; finding them needs an on-chain read, which was not part of this step.
- The sub-verifier admin listed in the repo is `0x2000ab040a899f914D6DfD2457C3dFBB22d4c762`.
- Whether these are multisigs or timelocks is UNCONFIRMED.

**What a new-chain deployer must do to keep it current** (from the contracts above; the operating details are UNCONFIRMED)
1. Deploy `RootRegistry` and a `RegistryInstance` for each of certificate (1) and circuit (2). Add sanctions (3) and attestation revocation (4) only if those features are used.
2. Deploy the `HonkVerifier` set, a `SubVerifier` (with `addProofVerifiers` mapping vkeyHash to verifier), `RootVerifier` and `VerifierHelper`.
   - Deploy scripts: `packages/registry-contracts/script/Deploy*.s.sol` and `circuits/src/solidity/script/Deploy*.s.sol`.
3. Run an **oracle** that watches ZKPassport's registries on Ethereum, Base or IPFS and posts each new root, with its timestamp, leaves and cid, to Lightchain.
   - New country certificates and new circuit versions arrive over time. If the mirror lags, proofs built against a newer root are rejected.
   - The helper script `script/test/get-latest-roots.sh` exists in their repo but was not read. UNCONFIRMED.
4. Hand admin to a timelock or DAO. Every contract has `transferAdmin(newAdmin)`, which is a one-transaction handover and matches our continuity goal.
5. When ZKPassport ships a new circuit version, deploy the new `OuterCountN` verifiers and register them, or new proofs will not verify.

## 3. Nullifier (unique identifier)

**How it is derived**
- "The unique identifier is derived from the ID data (retrieved from the chip). This data is combined with the domain name and the scope the service specified and hashed using Poseidon2." Source: docs FAQ, https://raw.githubusercontent.com/zkpassport/zkpassport-docs/main/docs/faq.md
- In the contract, scope = `sha256(domain) >> 8` and subscope = `sha256(scope) >> 8`. Both are checked in `SubVerifier._verifyScopes`.

**Scoping**
- It is scoped to **domain + scope**.
- It is **not** scoped to chain ID or wallet. Those are separate "bound data" (`senderAddress`, `chainId`, `customData`) that the app must check itself.

**Per document, not per person**
- "A person can have multiple IDs ... it won't be exactly that but more `one ID <-> one account`." Source: https://raw.githubusercontent.com/zkpassport/zkpassport-docs/main/docs/examples/personhood.md
- The docs recommend FaceMatch for stronger personhood.
- The default identifier can be recomputed by anyone with full chip data, including the issuing government. A **salted** identifier (vOPRF) prevents that, but it requires strict FaceMatch and a configured OPRF key (`globalOPRFPubKeyHash` in `SubVerifier`).

**Nullifier types** (API docs enum)
- `NON_SALTED = 0`, `SALTED = 1`, `NON_SALTED_MOCK = 2`, `SALTED_MOCK = 3`, `NONE = 4` (no identifier).
- Source: https://raw.githubusercontent.com/zkpassport/zkpassport-docs/main/docs/api.md

**Telling a mock proof from a real one**
- "All mock passport proofs have 1 as unique identifier." The fake-issuer (ZKR) certificates are only in the Sepolia registry, not mainnet. Source: https://raw.githubusercontent.com/zkpassport/zkpassport-docs/main/docs/getting-started/dev-mode.md
- `SubVerifier` reverts with "Mock proofs are only allowed in dev mode" unless `serviceConfig.devMode` is true.

**Checks our registry contract must do** (from `SubVerifier.sol`, `onchain.md` and `DateUtils.sol`)
1. Call `verify()` and `require(verified)`.
2. **Build `serviceConfig` inside our contract**, not from user input:
   - our fixed `domain` and `scope`
   - `devMode = false`
   - our own `validityPeriodInSeconds`

   The SubVerifier comment recommends setting domain and scope in-contract, or checking `helper.verifyScopes(publicInputs, domain, scope)`.
3. **Mock rejection:** `devMode=false` already rejects mock types, and mainnet roots exclude the fake issuer. Also `require(uniqueIdentifier != bytes32(uint256(1)))` as a belt-and-braces check.
4. **Reject "no identifier" proofs:** `SubVerifier` accepts `NONE_NULLIFIER`, so our contract must require the nullifier type to be `NON_SALTED` (or `SALTED`) and `uniqueIdentifier != 0`.
   - The type is read from `publicInputs[len-4]`.
5. **Wallet binding:** `helper.getBoundData(committedInputs).senderAddress == msg.sender`.
6. **Chain binding:** if bound, `boundData.chainId == block.chainid`. Otherwise check `customData` (for example "lightchain:9200"). See the SDK gap in section 4.
7. **Freshness:**
   - The verifier already enforces `proofDate <= block.timestamp < proofDate + validityPeriod` (`DateUtils.isDateValid`).
   - The proof timestamp is also readable with `helper.getProofTimestamp(publicInputs)`.
   - Source: https://raw.githubusercontent.com/zkpassport/zkpassport-packages/main/packages/registry-contracts/src/lib/DateUtils.sol
8. **One per human and lost-wallet move:** store `nullifier → wallet` and `wallet → nullifier`.
   - A second wallet with the same nullifier and no "move" intent is rejected.
   - A move re-proves from the new wallet, clears the old wallet, then sets the new one. This is our design, not ZKPassport's.

## 4. Client side (how a website asks the user to prove)

**Packages**
- `@zkpassport/sdk` (core) and `@zkpassport/ui` (the "Verify with ZKPassport" button).
- There is also a CDN script, `https://cdn.zkpassport.id/ui/v1.js`.
- No API key or account is needed to start. Branding comes from an optional dashboard.
- Source: https://raw.githubusercontent.com/zkpassport/zkpassport-docs/main/docs/getting-started/quick-start.md

**Flow**
1. The button opens a hosted popup at `verify.zkpassport.id`. Alternatively, `zkPassport.request({...})` returns a `url` that you show as a **QR code** (desktop) or a **link** (on phone).
2. The user opens the **ZKPassport mobile app** (iOS and Android), scans the MRZ, then taps the passport or ID **NFC chip**.
3. The app generates the proofs on the phone. The SDK fires `onRequestReceived`, `onGeneratingProof`, `onProofGenerated`, then `onSuccess({proofs, result})`, carried over a WebSocket "bridge".
4. For on-chain use, set `mode: "compressed-evm"`, pick the proof whose name starts with `outer_evm`, call `getSolidityVerifierParameters({proof, scope, devMode})`, and send it to the contract.

Source: https://raw.githubusercontent.com/zkpassport/zkpassport-docs/main/docs/getting-started/basic-usage.md

**Binding**
- `.bind("user_address" | "chain" | "custom_data", value)`, max 500 bytes total.
- `chain` only accepts a fixed `SupportedChain` list (ethereum, base, arbitrum, optimism, polygon, celo, gnosis, scroll, linea, world_chain, their testnets, and "local"). **Lightchain is not in it.**
- The button's `bind.chainId` is typed as a plain `number`. Whether 9200 is accepted end-to-end is UNCONFIRMED.
- Source: `api.md`.

**Test / mock mode**
- In the app: long-press above "Scan your ID", or Settings → Developer Options → Enable Developer Mode. This loads fake "Zero Knowledge Republic" IDs.
- In the SDK: `devMode: true`.
- Source: `dev-mode.md`.
- ZKPassport also runs a public demo page at https://demo.zkpassport.id (linked from the FAQ and the homepage; not opened).
- **For our browser demo:** we can copy the shape of this flow (QR → "request received" → "generating proof" → result plus code), entirely with pretend data. No ZKPassport service is needed.

## 5. Anything that blocks deploying the verifier ourselves on another EVM chain

**No hard blockers found.**
- **License:** Apache-2.0 allows redeploying and modifying. We must keep the license and copyright notices (Aztec for the verifiers, ZKPassport for the rest) and mark any changes.
- **Hard-coded chain IDs:** none in `HonkVerifier`, `SubVerifier`, `RootRegistry`, `RegistryInstance` or `DateUtils` as read. The only chain-specific items are the RPC/Etherscan entries in `foundry.toml` (deploy tooling only) and the deterministic `0x1D00…` addresses, which we would not reuse.
- **Built for this:** "This project holds ZKPassport's Solidity verifiers ... and the deployment scripts to deploy them on any EVM chain." The homepage says "Onchain verifiers for Ethereum, Base, Aztec and other EVM chains." Sources:
  - https://raw.githubusercontent.com/zkpassport/circuits/main/src/solidity/README.md
  - https://zkpassport.id

**Practical dependencies and risks (not legal blockers)**
1. **Root mirroring oracle:** someone must run it and fund its gas forever, or until the Lightchain team or DAO takes it on.
2. **Version churn:** the repo shows sub-verifier version `0.23.0` on Ethereum and `0.20.0` on Base. New circuit versions need new verifiers registered on Lightchain.
3. **SDK chain list:** it does not include Lightchain. Use wallet plus custom-data binding instead.
4. **SDK verifier address:** `getSolidityVerifierDetails()` returns ZKPassport's address. Our frontend must point at our own Lightchain address.
5. **EVM version:** they compile with solc 0.8.30. Whether Lightchain supports the newest opcode set (Cancun/Prague) is UNCONFIRMED. Compiling with an older `evm_version` (for example paris or shanghai) avoids that risk.
6. **Domain lock-in:** codes depend on the website domain, so the domain choice is permanent.
7. **ZKPassport services still used off-chain:** the mobile app, the `verify.zkpassport.id` popup, the WebSocket bridge and, for compressed proofs, their cloud prover (`cloudProverUrl`).
   - `bridgeUrl` and `cloudProverUrl` can be overridden ("contact us"), and repos for `cloud-prover` and `mobile-app` exist in the org.
   - Fully self-hosting these is UNCONFIRMED.
